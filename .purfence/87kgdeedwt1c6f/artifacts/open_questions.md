# 开放问题（Open Questions）

## 说明

本 PRD 采用方案 A（扩展 Task 工具），通过更新紫微的 prompt 文档来暴露文件操作能力。由于这是零代码改动的方案，且充分复用了现有基础设施，因此没有需要用户确认的 blocking 问题。

以下问题已在 PRD 中做出决策和假设，如果后续实施过程中发现需要调整，可以重新评估：

---

## Q1：用户体验是否足够好？（已决策）

**问题描述**：方案 A 需要两步调用（紫微 → Task → 子 Agent），相比直接工具调用可能体验稍差。

**决策**：采用方案 A

**理由**：
1. 零代码改动，快速交付，可立即验证
2. 符合主流三层架构模式（编排器 → 领域 Agent → 工具 Agent）
3. 安全隔离更好，文件操作在独立进程中执行
4. 可根据用户反馈后续迭代，必要时考虑方案 B

**验证方式**：P0 实施后收集用户反馈，如果体验问题确实影响核心价值，再评估方案 B

---

## Q2：是否需要创建专门的 file-explore agent？（已决策）

**问题描述**：default agent 已经具备完整工具集，但可能不如专门的文件操作 agent 高效。

**决策**：使用 `subagent_type='default'`

**理由**：
1. default agent 已具备 Claude Code SDK 的完整内置工具（Read、Write、Grep、Glob、Bash 等）
2. 足以覆盖大部分文件操作需求
3. 避免创建和维护额外的 agent 定义文件
4. 可根据后续使用情况优化

**验证方式**：观察 default agent 在文件操作场景下的表现，如果发现明显不足，再考虑创建专门 agent

---

## Q3：是否需要限制紫微可访问的文件路径？（已决策）

**问题描述**：紫微通过 Task 工具可以访问用户项目目录外的文件，可能存在安全风险。

**决策**：在 prompt 中添加安全指导，暂不在代码层面限制

**理由**：
1. 子进程隔离本身已提供一定安全保护
2. 用户主要是访问自己的项目目录
3. 代码层面限制会增加复杂度
4. 可在 prompt 中指导紫微避免访问敏感路径

**验证方式**：监控实际使用情况，如果出现安全问题再考虑添加路径限制

---

## Q4：是否需要在 P0 阶段实现 renderArtifacts 集成？（已决策）

**问题描述**：代码文件高亮展示需要调用 renderArtifacts，这增加了 P0 的复杂度。

**决策**：renderArtifacts 集成放入 P1 阶段

**理由**：
1. P0 阶段目标是验证核心功能可行性
2. 代码高亮是体验优化，不影响核心价值
3. 先让基础功能跑通，再优化展示效果
4. 分阶段实施降低风险

**验证方式**：P0 阶段用文本展示代码内容，P1 阶段再集成 renderArtifacts

---
